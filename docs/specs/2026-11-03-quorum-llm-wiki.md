# Quorum database-backed LLM Wiki design

## Selected architecture

Retain sources in a separate private immutable `knowledge_sources` table. Reuse existing `knowledge_entries` and `knowledge_revisions` for wiki pages and their attributable history. Central RPC guards enforce evidence and visibility rules for both existing and new callers. This extends the existing project authorization and CAS model without a parallel page store.

The shared-entry source variant was considered but rejected: an independently immutable source table makes the retention contract explicit and avoids source mutations through legacy page operations.

## Storage and RPC contract

Reuse `knowledge_entries` UUID as permanent page identity, existing Markdown `knowledge_revisions.body`, type/status/author/history, `knowledge_scope`, receipts, entry lock and expected-revision CAS. Do not add a parallel page store or new permissions. Add immutable `entry_kind` (`legacy`, `wiki_page`) to entries; old entries remain legacy, with no legacy-to-wiki conversion in this version. Titles may change; IDs cannot. No slug necessary for v1.

Add private `knowledge_sources` with `(space_id, source_id)` identity; original reference <=512 chars, evidence author <=200 chars, evidence timestamp (required explicit timestamptz), retained text <=8192 UTF-8 bytes, excerpt flag and scope description <=512 chars, server-calculated SHA256 of exact UTF-8 text, capturer user/agent/quorum and server capture time. Distinguish evidence author/date assertions from authenticated capturer and server time. Store originals or explicitly scoped excerpts, never pretend an excerpt hash identifies the whole original. Immutable content/attribution columns: corrected content creates another source UUID. Mutable withdrawal marker only; owner purge removes retained text/metadata through the explicit admin path. RLS and table grants follow current private-table policy. Revisions and source immutability need database-side enforcement, not CLI promises.

Add `source_ids` and `related_pages` bounded UUID arrays to revisions (<=8 each); include them in revision content hash. Keep current `conflicts_with` and `replacement_id` as the authoritative conflict/supersession relationships rather than duplicate link tables. Strictly validate every source/page target in the same space, source active, page not withdrawn; allow superseded pages as evidence/navigation targets with their status visible. Reject self links and duplicate IDs. Enforce relation validation on the server in the same transaction as revision creation, locking targets against withdrawal/purge races in a consistent order. Store links per revision so evidence changes are attributable.

Exact new operations (all use existing agent/session identity and scope):

- `knowledge_source_write(agent_id, session_ref, space_id, payload, request_id)`; payload `{source_id, reference, author, source_date, body, is_excerpt, excerpt_scope}`. Writer authority; create-only; identical request replay returns original identifier/hash receipt; different bytes/metadata for existing UUID rejected. Separate same-content sources are permitted when provenance differs.
- `knowledge_source_read(agent_id, session_ref, space_id, source_id, offset=0, length=4096, audit=false)`; current scope first, normal active only, audit owner only. Return source metadata/hash plus bounded retained text slice. No external URL fetching.
- Extend existing `knowledge_write` propose/revise payload with `entry_kind` only at propose, `source_ids`, `related_pages`. Wiki revisions require >=1 active retained source. Revise must supply complete evidence/link metadata explicitly; never silently clear it. Preserve existing verify/dispute/supersede/withdraw transitions and verification authority. Owner assertion remains required for owner verification.
- Extend `knowledge_admin` with `withdraw_source` and `purge_source` (source UUID; source immutable hash as expected identity); both owner-only explicit actions. Withdrawing a page does not implicitly withdraw independently retained shared sources; withdrawing a source must not leave its text accessible through dependent pages (see below).
- `knowledge_catalog(agent_id, session_ref, space_id, after_id=null, limit=5, context_budget=3000)`; stable UUID keyset pagination, limit 1–10, budget 512–6000 serialized characters including envelope. Metadata only: UUID, title, type, status, revision/hash, timestamps; no graph expansion. Opaque/no-authority cursor or UUID cursor scoped afresh on every call. Explicit `next_cursor` and `truncated`; never imply exhaustion when first item cannot fit.
- Extend existing `knowledge_read/search` projection to include retained sources and filtered related/conflict/supersession links. Keep lexical/exact search as default, no automatic vectors/model invocation. Search remains <=10 records/6000 serialized chars, excerpt <=600 chars; read/source body slices <=4096 chars and bounded metadata. Catalog/search should clearly identify legacy vs wiki entries.

## Mandatory closure of alternate paths

The existing public `knowledge_write` must enforce the wiki contract itself. A new wiki wrapper is insufficient: legacy revise currently defaults missing `source_refs` and `conflicts_with` to empty arrays (SQL lines 248–249), so it could erase evidence or edit an immutable source if sources were implemented as ordinary entries. Immutable entry kind must not be caller-convertible; reject source IDs in ordinary page mutation routes if sources share a namespace/store.

Use one shared server-side serializer/visibility predicate for catalog, read, search and relation projections. Current `knowledge_search/read` expose raw `conflicts_with` and `replacement_id` without checking current target visibility; purged/withdrawn target IDs can survive in another revision. Filter UUIDs, metadata, inverse supersedes and source references consistently, including old revisions. Return at most eight inverse supersedes IDs in deterministic UUID order with an explicit `supersedes_truncated` boolean; catalog constructs metadata directly without expanding this graph. Internal references must resolve through IDs, not authoritative raw URI strings in `source_refs`. Arbitrary external URLs remain untrusted cited data.

For predictable v1 withdrawal semantics, suppress normal retrieval of a wiki page whose selected revision references a withdrawn/purged source. Return a fixed unavailable diagnostic on direct read; never reveal hidden source IDs/counts or a title/excerpt before filtering. Explicit authorized revision can replace the invalidated source and return the page to proposed. Owner audit preserves the history until explicit purge. This avoids source text surviving as a synthesized excerpt in dependent page reads. State the limit clearly: already delivered information cannot be recalled; arbitrary copied strings outside structured evidence cannot be reliably tracked. Withdrawal must also invalidate/exclude affected page vectors. Do not accidentally classify missing legacy sources as retained wiki sources.

Superseded evidence is deliberately different from withdrawal: permit authorized read of the superseded entry's current revision (with `superseded` label and visible replacement), while preserving owner-only access to arbitrary old revisions. Search/catalog may exclude superseded pages by default but links must allow bounded follow-up reading. Conflicting pages remain disputed/proposed unless owner verification explicitly decides otherwise. Revise/dispute cannot silently turn a conflict into verified fact.

## Acceptance risks and concrete tests

1. SQL tests must exercise direct legacy RPC calls, not just new Python commands: attempts to remove evidence, change immutable source bytes/author/date, change page kind, cross-space links, targets withdrawn concurrently, and stale request replay after permission revocation.
2. Test all output paths after source/page withdrawal, purge, grant revocation, detach and device/membership revocation: catalog, search metadata, read slices, source read, forward/inverse links, superseded navigation, historical audit and receipt replay. No hidden target UUID/title/hash should leak through structured projections.
3. Reuse existing two-process CAS test but assert wiki source/link history: simultaneous same-base updates => one success, one stale rejection; reconcile from winning revision; old source/link revisions retained. Include link/source hash in the assertion.
4. Verify source evidence date and capturer time are separate, excerpt scope survives, hash computed server-side, malformed/oversize Unicode payloads fail, full output envelopes meet documented limits, and empty-budget pagination cannot loop without explanation.
5. Existing backend runner explicitly appends one knowledge migration; update fixture discovery to apply the additive migration too. Passing the old test harness alone does not exercise new SQL.
6. Real qualification still needs retained material result, later attached authorized quorum answering from page/source, conflicting/superseded evidence demonstration and bounded real-question relevance/context measurement. Existing manual-vector tests do not prove paraphrase quality. Current issue explicitly says cross-human live isolation was not qualified; retain that limitation until exercised.
7. Update English plan and installed workflow around catalog -> search/read sources/current page -> source retention -> CAS update -> bounded answering. Both clean individual Codex/Claude installs need success, denied access, and optional-feature-unavailable paths. Capture grant must guard source retention as well as page proposal at transport boundary; introduce an explicit capture-source action or composition through existing guard, never treat source ingest as exempt capture.
8. Ship through all pinned repository gates, independent review and required CI/PR. Issue edit alone does not authorize live DDL or provider spending. No new embedding provider, model, listener or background synthesis is part of this design.

Design inputs: existing project-knowledge SQL, Python payload routing and exact capture guards, SQL lifecycle and two-process CAS tests, and the revised issue #59. Implementation and live acceptance are tracked separately.

## Approach and authority

Owner issue59 selects database-backed wiki and defers embeddings; autonomous implementation is authorized. Implementation choice: retain sources in a separate private immutable table, reuse existing entries/revisions for wiki pages. A wrapper-only design is rejected because old RPCs would bypass evidence rules; a separate page store duplicates access/CAS. No frontend, filesystem sync, provider generation or automatic chat ingestion. No live DDL until the exact reviewed migration is ready for the owner's deployment decision.
