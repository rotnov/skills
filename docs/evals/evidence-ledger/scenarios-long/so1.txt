== D6: Tern documentation, performance page
Tern documentation, performance page

Last edited for release line 4.x. If you are reading an archived copy, check the version selector in the top bar before following any links on this page.

This page belongs to the Operations section, alongside Monitoring, Upgrades, and Backup and Restore. The Operations section assumes you have already completed the Quickstart and have a running cluster with the admin CLI installed. Command examples use the tern-admin binary; on Windows hosts, substitute tern-admin.exe. Configuration keys are written in dotted form, for example log.retention.hours, and can be set either in tern.toml or through environment variables with the TERN_ prefix.

The default configuration fsyncs each batch before acknowledging. Reference throughput on 3 nodes: 49k to 55k msg/s.

For questions about the admin CLI itself, see the CLI reference, which lists every subcommand with its flags. Shell completion scripts for bash, zsh, and fish are shipped in the contrib directory of the release tarball.

The Monitoring page describes the built-in metrics endpoint, which listens on port 9464 by default and exposes counters in the Prometheus text format. Dashboards maintained by the community are linked from the project wiki; they are not reviewed by the core team.

Found a mistake on this page? Documentation lives in the docs folder of the main repository. Open a pull request against the main branch and tag it with the docs label. Typo fixes do not need an issue first. The docs team triages new pull requests every Tuesday and Thursday.
== D7: Internal requirements, payments events
Internal requirements, payments events

Owner: Payments Platform team. Document status: living draft, reviewed at the start of each planning cycle. Comments go in the shared review thread rather than inline, so edit history stays readable.

Scope: this page covers the event stream produced when a payment is authorized, captured, refunded or disputed. Card tokenization events and the merchant onboarding flow are documented separately and are out of scope here.

Naming: event types use lowercase dotted names, for example payment.captured or refund.issued. Field names are snake_case. Amounts are integers in minor currency units with an ISO 4217 code alongside. All timestamps are UTC in RFC 3339 format.

Requirements:

Delivery: at-least-once. No acknowledged message may be lost on node power failure, so fsync before ack is mandatory. Peak 30k msg/s today, forecast 40k next year.

Data handling: events must not carry full card numbers, CVV values or raw bank account numbers. Customer email addresses are allowed only in the dispute events, where the support tooling needs them. Access to dashboards built on the stream is granted through the usual request form.

Schema changes: additive fields may ship at any time. Removing or renaming a field requires a deprecation notice in the team channel and sign-off from both the Ledger and Reporting teams.

Contacts: on-call rotation is listed in the paging tool under payments-platform. For questions about reporting consumers, ask the Finance Engineering group.

Open items: confirm the field list for partial refunds; agree a shared glossary with Risk.
