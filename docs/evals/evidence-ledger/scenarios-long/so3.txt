== D1: Kestrel changelog, 2.8.0
Kestrel changelog, 2.8.0

Released 2026-10-28. Thanks to everyone who filed reports and tested release candidates over the past six weeks. Packages are available for Debian 12, Ubuntu 24.04, Rocky 9 and as a container image on the usual registry.

New:
Added a --json flag to kestrelctl status and kestrelctl volumes list for easier scripting (4302).
The metrics endpoint now exports per-tenant request latency histograms with configurable buckets (4318).
The admin web console gains a dark theme and remembers column widths between sessions (4355).

Changed:
Default log rotation size raised from 64 MB to 256 MB (4290).
The minimum supported Go toolchain for building from source is now 1.23.

Fixed: race in stripe rebuild that could drop a parity shard when a node is replaced during an in-flight write (4411).
Fixed: kestrelctl user create no longer prints the generated secret twice when stdout is not a terminal (4380).
Fixed: the S3 gateway returned 500 instead of 404 for HEAD on a missing bucket with a trailing slash (4392).
Fixed: the timezone setting was ignored in audit log timestamps when exporting from the web console (4407).

Docs: rewrote the quota configuration guide and added examples for nested tenants.

Known issues: the dark theme does not yet apply to the embedded Grafana panels. This will be addressed in 2.8.1.

Checksums and signatures for all artifacts are published alongside the packages. Please report problems on the issue tracker and include the output of kestrelctl version.
== D2: Community forum answer
Re: Odd warnings after upgrade, plus a couple of other questions

Posted by mtarvo, Tue 10 Nov, 21:47

Catching up on this thread after a long week, so apologies for the wall of text. Taking your points in order.

First, the noisy log lines about clock skew. Those come from the monitoring agent, not the cluster itself. Point all hosts at the same NTP pool and they should disappear within an hour or so. We had the same thing on our lab boxes last spring, and it was purely cosmetic.

Second, the dashboard graphs going flat overnight. That is the retention default on the metrics exporter, which keeps fourteen days at one-minute resolution and then downsamples. Bump it in the exporter config if you want longer history. On our setup it costs roughly 2 GB per month, so nothing dramatic.

Third, the old issue you linked from the mailing list archive.

That was 4411, fixed in 2.8 per the changelog. You are fine on anything from 2.8 up.

Unrelated, but since you mentioned the new rack: check the PDU firmware before you mount anything. Two of ours shipped with a version that reported phantom overcurrent alarms every few hours, and support took about three weeks to send a patched image. Also label both ends of every cable. Future you will be grateful at 2 a.m.

On the meetup question, the next one is in Leeds on the 28th. The sign-up sheet is pinned in the events subforum, and there are still around fifteen seats left. Bring a laptop if you want to join the dashboard templating session in the afternoon.

== D3: Blog post "Running Kestrel in production"
We have been running Kestrel for a little over two years now, and a few people asked me at the last meetup what our day-to-day looks like. This is not a tuning guide, just a loose collection of notes from a small team that would rather sleep through the night.

Monitoring first. We scrape the built-in metrics endpoint every fifteen seconds and keep about thirty days of history. The three panels we actually look at are request latency at p99, disk usage per node, and the client connection count. Everything else lives on a second dashboard that nobody opens unless something is already on fire.

Logging was noisier than expected out of the box. We dropped the default level to warn and ship logs to our usual aggregator, which cut volume by roughly 80 percent.

The scary rebuild bug is gone since 2.8 (see the release notes), so node replacement is routine now.

On the client side, we standardized on the official Go library after a short experiment with a community Python wrapper. Connection pooling defaults were fine for us; we only raised the timeout from two seconds to five for a batch job that runs overnight.

Config lives in the same repo as our other infrastructure, reviewed like any other change. We template it per environment and keep staging deliberately small, three nodes on cheap instances, mostly to catch typos.

Finally, on-call. Kestrel pages us maybe twice a month, almost always for disk alerts we set too conservatively. If you are starting out, write the runbook before the first page, not after.
