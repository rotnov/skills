# Allocation and Verification

## Effort and decisions

Predeclare rounds, concurrency, bounded tasks, and investigation allowance;
reserve effort for alternative exploration, preparing checkable artifacts,
verification, corrections, and reporting. Use actual host-enforced token or
spending limits where available. Otherwise bound observable work and report
unknown costs; behavioral limits are not a hard financial guarantee. A required
monetary ceiling needs suitable enforcement before paid execution.

Choose the next probe by decision impact, uncertainty resolved, methodological
novelty, cost, and duplication. These are qualitative judgments, not probabilities.

| Decision | Reason |
| --- | --- |
| Continue / deepen | A concrete next probe or stronger verification can change the decision. |
| Split | Distinct questions can progress within the same research program. |
| Hybridize | Combining findings offers a new mechanism; retain both parent lineages. |
| Enable | A bounded auxiliary problem could unblock the parent through an explicit transfer. |
| Redeploy | Evidence changes where already-authorized effort is useful. |
| Park | No justified next probe, a missing prerequisite, or exhausted allowance. |
| Reframe | The proposed alternatives do not address the actual goal. |
| Finish | Acceptance is supported, or the limit requires a partial result. |

Record each material decision's actor, rationale/evidence, target problems/islands,
old/new allotments, remaining envelope, and authority. Preserve finite checking
and alternative reserves. Do not fund repeated arguments as independent evidence.
A longer authorized allowance overrides the two-round starting default. At the
limit, stop dispatching and report gaps; extending scope or spending needs new
authority. No unrestricted recursion or automatic model upgrade follows from
this protocol.

## Verification package

Prepare a compact handoff before acceptance:

| Fields | Meaning |
| --- | --- |
| `candidate`, `problem_id`, `claim_revision` | Exact assertion/implementation and addressed formulation. |
| `assumptions`, `relation_to_goal` | Applicability and justified connection to the user's criterion. |
| `argument_or_implementation` | Inspectable substantive candidate. |
| `checkable_artifact`, `input_revisions` | Authorized artifact locations and exact inputs where available. |
| `verifier_configuration` | Checker/tool and epoch, including known shared dependencies. |
| `procedure`, `observed_outcome` | Reproducible check, what actually ran, and its result. |
| `unchecked_obligations` | Missing checks, transfer conditions and unestablished claims. |

Apply two separate acceptance gates:

1. **Artifact validity:** Does the artifact support its stated result under the
   recorded assumptions at the claimed evidence level?
2. **Goal correspondence:** Does that result satisfy the user's actual criterion
   and all required transfer obligations?

A checker accepting sorted-input correctness cannot establish arbitrary-input
correctness. Inspect a formal statement and its assumptions/admitted obligations,
not just the success indicator. Finite passing tests are not universal proof;
LLM review is not a formal certificate. For code, run relevant authorized tests;
for documentary research, inspect primary sources and scope. Set the required
check from the agreed criterion: a literature inquiry may finish with an
attributed documented capability or reported implementation. Our reproduction is
a separate claim; require it when the task asks for it or the conclusion depends
on it, rather than silently adding hardware testing to documentary acceptance.
When source inspection can still resolve the question, pursue that bounded check
before handing off an experiment. Unavailable required checks leave only the
affected acceptance provisional, without erasing established findings.

Use a fresh-context verifier when available and disclose shared dependencies.
An adversarial check targets a decision-changing assumption with an actionable
counterexample or experiment; it is not an obligation to manufacture objections.
Single-context checking is self-review, not independent validation.

## Decision report

State the answer and scope first. For each decision-changing claim, give its
supported/contradicted/unresolved verdict, evidence basis, attribution, and
remaining condition. Distinguish "documented by the implementation author" from
"reproduced by us" and from "verified for your configuration." Explain what the
available evidence lets the user conclude now, then the next check for any gap.
Report formulation coverage, decisive evidence,
island comparison and shared roots, both gates, remaining contradictions and
transfer obligations, actual usage or unknown, execution mode and independence
limits. Include the next discriminating action for unresolved work and novelty
status only when making that claim. Use links to approved detailed artifacts.
Keep task completion, support for the conclusion, and permission to act distinct.
